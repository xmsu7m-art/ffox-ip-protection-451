# Analysis: Why the Built-in VPN Token Endpoint Returns 451

This document expands the evidence summarized in the README. All requests were
made on 2026-10-21 from a residential China Mobile line in Guangdong (AS9808),
using the browser's built-in VPN client and ordinary HTTPS requests. No proxy was
involved unless stated.

---

## 1. Scope

Three questions were investigated:

1. Does an authenticated request to `/api/v1/fpn/token` behave differently from
   an anonymous one?
2. Is there another endpoint that issues a ProxyPass?
3. Does the `experiment` query parameter influence the region decision?

The short answers are: the token is irrelevant on the lowercase path; there is
no second endpoint, but there is a second path to the same endpoint; and the
parameter has no effect.

---

## 2. The 451 is an edge rule, not an authorization decision

### 2.1 Response fingerprint

| | `GET /api/v1/fpn/token` | `GET /API/v1/fpn/token` |
|---|---|---|
| Status | `451` | `400` |
| `Server` | `Varnish` | `nginx` |
| `Via` | `1.1 varnish` | `1.1 google, 1.1 varnish, 1.1 varnish, 1.1 varnish` |
| `X-Served-By` | one POP (`cache-sin-...`) | four POPs (`cache-bfi-...` x3, `cache-sin-...`) |
| `Content-Security-Policy` | absent | helmet default set |
| `Set-Cookie` | absent | `session=...; HttpOnly; Secure` |
| `Connection` | `close` | `keep-alive` |
| `Retry-After` | `0` | absent |
| Body | `{"error":"unavailable_in_region"}` | `{"error":"Bad Request: Missing Authorization header"}` |

The 451 has no Google hop, no origin CSP, no cookies, and a single edge POP. It
is generated by Fastly VCL before the request enters the origin.

### 2.2 Authorization does not change it

Two requests were compared:

- no `Authorization` header -> `451`, 33-byte body;
- a syntactically valid but bogus JWT -> `451`, byte-for-byte the same body.

The edge does not parse the token. Whatever the account entitlement is, the
lowercase path is rejected first.

---

## 3. The rule is case-sensitive and matches the raw path

| Path | Status | Answered by |
|---|---|---|
| `/api/v1/fpn/token` | 451 | edge |
| `/api/v1/fpn/does-not-exist-xyz` | 451 | edge (so it is a prefix rule, not a route guard) |
| `/api/v1`, `/api/v1/` | 451 | edge |
| `/api/v2/fpn/token` | 451 | edge |
| `/api/fpn/token` | 451 | edge |
| `/api/v1//fpn/token` | 451 | edge |
| `/api/v1%2Ffpn/token` | 451 | edge |
| `/api%2Fv1/fpn/token` | 404 | origin (the literal `/api/` prefix is gone) |
| `/Api/v1/fpn/token` | 400 | origin |
| `/API/v1/fpn/token` | 400 / 401 / 200 | origin |
| `/%61pi/v1/fpn/token` | 400 | origin (decoded to `/api/` after the edge) |
| `/api/V1/fpn/token` | 451 | edge |

The `/api%2Fv1/...` case is the clearest proof: the rule inspects the raw URL
string, not the decoded route.

### 3.1 Why the origin accepts the case variant

The origin response headers are a textbook Express/helmet fingerprint
(`x-dns-prefetch-control`, `x-download-options`, `origin-agent-cluster`,
`x-permitted-cross-domain-policies`, `cross-origin-opener-policy`,
`cross-origin-resource-policy`). Express's router defaults to
`caseSensitive: false`, so `/API/v1/fpn/token` and `/api/v1/fpn/token` map to the
same handler.

In other words: the edge is case-sensitive, the router is not, and the mismatch
is the bypass.

---

## 4. Reaching the handler from mainland China

With the case variant, every control-plane route answers from the origin:

| Request | Result |
|---|---|
| `GET /API/v1/fpn/token` (no credentials) | `400 Missing Authorization header` |
| `GET /API/v1/fpn/token` (bogus JWT) | `401 Unauthorized` |
| `GET /API/v1/fpn/status` (bogus JWT) | `401` |
| `POST /API/v1/fpn/activate` (bogus JWT) | `401 jwt malformed` |
| `GET /API/v1/fpn/auth?experiment=alpha` | `302` to `accounts.firefox.com/authorization?...` |

A real account OAuth token returns `200` with a ProxyPass JWT in the
`token` field, plus `X-Quota-*` headers.

---

## 5. No second endpoint

`vpn.mozilla.org` is the only live host. The following names do not resolve:

- `vpn.mozilla.com` (the hard-coded default in `GuardianClient.sys.mjs`)
- `vpn-api.mozilla.org`
- `api.vpn.mozilla.org`
- `guardian.mozilla.org`
- `vpn.stage.mozilla.org`
- `vpn-stage.mozilla.org`

`vpn.allizom.org` (the staging domain) resolves, but returns the same 451 and
the same case-sensitivity bug, which suggests the rule is shared across
environments rather than being a production-only mistake.

The OAuth callback `/oauth/success` is outside `/api/` and reachable, but it
only completes an account-service flow. The ProxyPass is issued solely by
`/fpn/token`.

Conclusion: there is no alternative credential endpoint. The only alternative is
the same endpoint through a different path spelling.

---

## 6. `experiment` does not affect the region decision

`GuardianClient.enrollmentURLs()` appends `?experiment=<type>` to
`/api/v1/fpn/auth`. Comparing the four constants:

| Value | Lowercase path | Uppercase path | `client_id` | `scope` | `redirect_uri` |
|---|---|---|---|---|---|
| alpha | 451 | 302 | `e6eb0d1e856335fc` | `profile ... subscriptions/iap ... subscriptions` | `https://vpn.mozilla.org/oauth/success` |
| beta | 451 | 302 | same | same | same |
| gamma | 451 | 302 | same | same | same |
| delta | 451 | 302 | same | same | same |

Only the trailing `experiment=` value differs. The region rule is evaluated on
the path at the edge, before the query string reaches the application, so the
parameter cannot change the outcome. It selects an account-service cohort, not a
region.

## 7. Making the client use the variant

`GuardianClient.sys.mjs` builds its URLs as:

```js
get #tokenURL() {
  const url = new URL(this.guardianEndpoint);
  url.pathname = "/api/v1/fpn/token";
  return url;
}
```

The pathname is assigned, so `browser.ipProtection.guardian.endpoint` can only
change the origin, not the case. Two options exist:

1. **Loopback shim (used here).** Point the preference at
   `http://127.0.0.1:8787/`; the shim rewrites the prefix and connects directly
   to `vpn.mozilla.org`. No browser internals are patched and the approach
   survives browser updates.
2. **Runtime monkey-patching.** Replace `fetchProxyPass` on the Guardian client
   instance. It works, but it duplicates the response parsing logic and breaks
   when the module changes.

The shim is the smaller and more durable option.

---

## 8. Remaining limits

- The mechanism depends on a vendor-side inconsistency. Either a
  `~*` VCL match or `caseSensitive: true` on the Express router would close it.
- The initial enrollment uses a hidden browser and an origin allow-list, so it
  cannot be performed through the loopback shim. Enroll once with a working
  network path, then switch the preference.
- This environment observed a successful `CONNECT` to the relay from the same
  client IP. Relay-side region policy was not independently characterized.
- Using the service outside its supported regions may conflict with the vendor's
  terms of service.

## 9. Reproduction

```bash
# edge vs origin
for p in /api/v1/fpn/token /api/v1/fpn/nope /api/v2/fpn/token \
         /API/v1/fpn/token /Api/v1/fpn/token /%61pi/v1/fpn/token; do
  printf "%-30s " "$p"
  curl -sS -o /dev/null -w "%{http_code}\n" "https://vpn.mozilla.org$p"
done

# authenticated comparison (requires an account token)
curl -sS -D - -H "Authorization: Bearer $TOKEN" \
  https://vpn.mozilla.org/api/v1/fpn/token
curl -sS -D - -H "Authorization: Bearer $TOKEN" \
  https://vpn.mozilla.org/API/v1/fpn/token
```

The first loop needs no account: a `400`/`401` instead of `451` means the
request reached the origin.
